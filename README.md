# 音频质量校验

拖拽式音频质量校验工具。把音频文件或文件夹拖进窗口，逐个音频出一行 CSV。

**两个项目，两个独立的程序，校验项完全不同，别拿错：**

| 程序 | 项目 | 一行 = | 校验项 |
|---|---|---|---|
| `AudioQC` | 音乐实录 | 一个音频（按歌分组，人声/伴奏轨联动） | 见下「音乐实录」 |
| `AudioQC-Raw` | 原始录音素材 | 一个文件（互不相关） | 见下「原始录音素材」 |

两个程序**分开发版**，Release 互不覆盖：项目 A 走 `.github/workflows/build.yml`，
tag 是 `latest` / `v*`；项目 B 走 `build-raw.yml`，tag 是 `raw-latest` / `raw-v*`。

代码上层各自独立、下层共用：

```
src/analysis.rs                     解码 + 声学指标计算（只测不判）★两个项目共用
src/util.rs                         字体/输出路径/写 CSV 等界面零件  ★共用
src/main.rs                         音乐实录的界面
src/analysis.rs::check_song         音乐实录的判定与阈值
crates/audio_qc_raw/src/check.rs    原始素材的判定与阈值
crates/audio_qc_raw/src/main.rs     原始素材的界面
```

改阈值只动对应项目那一个文件，不会串台。往 `analysis.rs` 里加东西时注意：那一层
只负责「测出数字」，「多少算合格」永远留在各项目自己的判定里。

## 校验项：音乐实录（AudioQC）

| 指标 | 要求 |
|---|---|
| 伴奏活动比例 | ≥ 80%（活动时长 / 整歌时长） |
| 人声活动比例 | ≥ 40% |
| 人声相对伴奏平均 RMS 差 | −15 ~ +10 dB |
| 截止频率 | ≥ 15 kHz |
| 码率 | ≥ 320 kbps |
| 人声底噪 | < −40 dBFS（界面可调） |
| 伴奏/合轨底噪 | < −40 dBFS（界面可调；合轨跟伴奏走同一条） |
| 平均幅值 | −26 ~ −3 dBFS（界面可调；**只卡人声和合轨，伴奏不判**） |
| RT60 | 每条轨 < 0.3 秒（任一条超标，整首歌不合格） |
| 峰值电平 | −3 ~ −1 dBFS |
| 削波 | 不允许 |

阈值都在 `src/analysis.rs` 顶部，CSV 表头在同文件的 `COLUMNS`。

## 校验项：原始录音素材（AudioQC-Raw）

CSV 列（交付方指定九个字段：文件类型 是否立体声 声道数 采样率 时长 静音比例
信噪比dB 频响 是否满足要求；文件名 / 采样位深 / 响度dB / 备注 是补充列）：

| 列 | 内容 | 要求 |
|---|---|---|
| 文件名 | 相对路径 | — |
| 文件类型 | `WAV/pcm_s16le` | 必须 WAV 且未压缩 PCM |
| 是否立体声 | `是` / `是(左右相同)` / `否` | 必须立体声 |
| 声道数 | 2 | = 2 |
| 采样率 | Hz | ≥ 44.1 kHz |
| 采样位深 | `16bit` / `24bit` … | ≥ 16 bit（硬判定，读不出只记备注） |
| 时长 | mm:ss | ≥ 1 分钟 |
| 静音比例 | % | ≤ 20% |
| 信噪比dB | 活动段 RMS − 底噪 | ≥ 70 dB |
| 响度dB | 活动段 RMS | ≥ −40 dB（**只记备注，不判不合格**） |
| 频响 | 实测带宽 `25Hz-22.1kHz` | 高频端 ≥ 20 kHz（±3dB 平坦度不判，见下） |
| 是否满足要求 | `是` / `否：原因…` | — |
| 备注（如有） | 这个文件可能有什么问题，一句一条 | — |

几点说明：

- **文件类型不看后缀**，读文件头的 `RIFF....WAVE`；「未压缩」单独看 symphonia
  认出的真实编码——`.wav` 里照样能装 ADPCM / A-law / 甚至 mp3。
- **是否立体声**和**声道数**是两列：双单声道（左右完全相同）声道数确实是 2，
  判定上不算不合格，但这一列会写 `是(左右相同)` 把它跟真立体声区分开。
- **频响**报的是实测带宽，不是照抄规格里的 `20Hz-20kHz`。低频端取内容真正
  延伸到的最低 1/3 倍频程带，高频端取砖墙检测的截止点。砖墙远低于奈奎斯特
  会判「疑似有损压缩来源」。
- **底噪没有单列一列**，信噪比不合格时会写进备注，否则光看一个 SNR 数字分不清
  是「底噪高」还是「录得太小声」。
- **采样位深**是硬判定项：读得出且 < 16 bit 直接判「否」；某些容器不写位深，
  这种情况留空并在备注提示人工确认。
- **响度**（活动段 RMS）低于 −40 dB 只在备注里提示「偏小声」，**不判不合格**，
  也不作退货依据——交付方要求 −40 dB 以上，但这项按软指标处理。

阈值在 `crates/audio_qc_raw/src/check.rs` 顶部，CSV 表头是同文件的 `COLUMNS`。
信噪比下限、静音比例上限、时长下限三项界面上可以现场改。

## 下载

去 [Releases](../../releases) 拿对应平台的包，或者在 Actions 里下最新构建产物。

两个程序在**不同的 Release 里**：音乐实录在 `latest` / `v*`，原始素材在
`raw-latest` / `raw-v*`。

- **macOS**：`AudioQC-macOS.dmg` / `AudioQC-Raw-macOS.dmg`（通用二进制，Intel 和
  M 系列都能跑）。双击挂载，把弹出窗口里的 `.app` 拖进 `Applications` 即可——
  **别点进 App 包内部**，直接拖那一个图标。首次打开提示"无法验证开发者"是正常的（未签名），
  右键点图标选**打开**即可，或终端执行 `xattr -dr com.apple.quarantine AudioQC.app`。
  > 用 IM 工具（微信等）转发给同事时也要发整个 `.app` 或这个 `.dmg`，
  > 不要从包内单独拷出可执行文件——那样对方双击时会被系统当成未知文件，
  > 交给文本编辑器打开，报"文本编码不适用"的错误。
- **Windows**：`AudioQC.exe` / `AudioQC-Raw.exe`，单文件直接双击。
- **Linux**：`AudioQC-linux` / `AudioQC-Raw-linux`，`chmod +x` 后运行。

## 几个指标的说明（音乐实录）

- **底噪**取整段音频静音部分的能量平均（静音段 = 活动门限以下、且高于 −90 dBFS 的帧，
  −90 以下是剪辑挖的绝对零，不是本底噪声）。静音总时长不足 0.5 秒就不报数，
  因为连续演奏的轨根本没有静音可测，硬报出来的只会是"最安静的乐句"。
  人声轨、伴奏/合轨用两套上限，都在界面上改；测不出底噪只记备注，不判不合格。
- **平均幅值**是活动段 RMS，只卡人声轨和合轨。伴奏轨仍然出数，但不参与合格判定。
- **RT60** 没有冲激响应可用，是从乐句衰减段用 T20 外推的估计值，只保留
  拟合优度 R² > 0.9、时长合理、且整段在底噪之上的衰减段。衰减段少于 10 段时
  会在结论里标"建议人工复核"。每条轨各自测量、各自卡 &lt; 0.3 秒；任一条超标，
  整首歌不合格。测不出只记备注，不判不合格。
- **截止频率**找 8 kHz 以上的"砖墙"跌落点取半功率点；没有砖墙就按满带宽算。
  偏保守，只会低报不会高报。
- **码率**按 文件字节数 / 时长 实测，VBR 拿到的是真实平均码率。
- **峰值电平** = `20·log10(max(|采样|))`，取解码出来的原始采样里绝对值最大的
  那一个。必须用原始采样，不能用程序内部为了对齐立体声/单声道响度而乘过增益
  的那份下混数据——用缩放过的会读出偏差接近 1dB 的假峰值（立体声轨、且左右
  声道不相关时最明显）。
- **削波**检测的是"连续多个采样贴着满量程附近"：逐声道扫描，采样绝对值
  ≥ −0.5 dBFS（约 0.9441）算"触顶"，连续触顶 ≥ 3 个采样算一次削波事件，
  中途掉出阈值就清零重新计数；孤立 1~2 个触顶采样只是正常的瞬时峰值，不算。
  阈值没有卡在数字满量程 0dBFS（−0.0087dB），是留了 0.5dB 的余量——很多削波
  发生在数字化之前（话筒前级/放大器过载），到 ADC 时可能还留着零点几个 dB
  没顶满，波形已经被削平但采样值够不到 0.999，卡满量程会整段漏检。
 

## 原始素材校验的两个已知局限

看这个工具的结论之前先读这两段，否则会对它的能力有错误预期。

### 频响 20Hz–20kHz ±3dB 测不出来

频响是录音**链路**的属性：用已知激励（扫频、粉噪）去激励，看输出偏离多少，才叫
频响。拿一段人声或音乐去算长时平均谱，得到的是**内容本身**的频谱——任何真实素材
都是低频重、高频滚降，离「±3dB 平坦」差三四十 dB。按字面判会全军覆没，而且那个
「不合格」不说明任何问题。

所以这条被拆成了两半：

- **带宽**（`频响` 列）实测并参与合格判定：高频端够不够 20kHz。
- **±3dB 平坦度不校验**。只在这个文件其余各项都通过时，备注里写一句
  「±3dB平坦度未校验，需录一段扫频测试音」——提醒别把那个「是」当成全部达标。

平坦度的算法（`flatness_db()`）代码还在，但没接进结果表：拿正常素材算出来的是
**内容本身**的频谱起伏，交付方看了也不能据此做任何决定，放进备注只是噪音。等交付
方开始每批附扫频/粉噪校准文件，把它接回去就能真算 ±3dB。

### 「未经算法处理」只查得到硬证据

判不合格的只有两样，因为只有这两样是实锤：

- 编码不是 PCM（直接违反「未压缩」）；
- 高频砖墙远低于奈奎斯特（这条轨过过有损编码）。

降噪、限幅、高通滤波在波形上只留统计线索，反推一定会误报——一条录得干净、本来
低频就少的人声，跟一条做过高通的，频谱上可以长得一模一样。所以这几项一律写进
**备注**交人工复核，不替人做「退货」的决定。

备注列的写法：只写「这个文件的事」，一句一条，不写行话（奈奎斯特、倍频程、
砖墙这些一律换成大白话，要讲原理来这份 README）。会出现的句子就这些：

| 触发条件 | 备注写什么 |
|---|---|
| 连续触顶采样 | 有 N 处削波，声音已经失真 |
| 峰值贴满量程 | 音量顶到最大，像是后期拉过响度 |
| 中段出现绝对数字零 | 中间有 N 秒完全无声，像是被降噪或手动静音过 |
| 低频比中低频低 25dB 以上 | 低频几乎没有，可能被滤掉了（也可能录的内容本来就没低频） |
| 左右声道能量差 < −60dB | 左右声道完全一样，实际听不出立体声 |
| 响度 < −40dB | 响度只有 −N dB，偏小声（要求 −40dB 以上，不作退货依据） |
| 没有静音段可估底噪 | 信噪比测不出：全程几乎没有安静的地方，要人工听一下 |
| 频谱算不出来 | 频响测不出：内容太短或几乎无声 |
| 容器不写位深 | 采样位深读不出：需人工确认是否 16 位以上 |
| 全程几乎没有信号 | 响度测不出：全程几乎没有信号 |
| 信噪比不合格 | 底噪 −N dBFS（分清是底噪吵还是录得太小声） |
| 44.1kHz 且高频卡在 19–21kHz | 44.1kHz 本来就到不了 20kHz，换 48kHz 录才有余量 |
| **其余各项全部通过** | ±3dB 平坦度未校验，需录一段扫频测试音 |

### 顺带一句：44.1kHz 卡不稳 20kHz

44.1kHz 的奈奎斯特是 22.05kHz，抗混叠滤波常在 20kHz 附近就开始滚降，离「高频到
20kHz」只剩 2kHz 余量。要稳过这条，实际得要求录 48kHz。工具会在备注里提醒，但
这是个规格层面的矛盾，得跟交付方对齐，不是改阈值能解决的。
